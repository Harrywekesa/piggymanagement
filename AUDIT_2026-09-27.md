## 3. Architecture assessment

### Strengths

1. **Clear layering intent:** UI → `MainViewModel` → `PHMSRepository` → Room DAOs, with **domain engines** (`PromotionEngine`, `OutbreakDetector`, `WithdrawalTracker`) separated from UI.
2. **Offline-first:** Local Room is the UI source of truth; Firestore sync is best-effort (appropriate for rural connectivity).
3. **Rich domain model:** Pigs, pens, batches, stages, feed, health, breeding, alerts, market, expenses — aligned with real pig operations.
4. **Spec docs match code direction:** Module breakdown and screens doc are unusually thorough for a student/innovation project.

### Weaknesses

1. **God files:** `Screens.kt` (~3.5k lines) and `MainViewModel.kt` (~874 lines) concentrate too much behavior; hard to test, review, and parallelize.
2. **No Hilt/Koin / no `viewModel()` factory:** ViewModel is constructed manually in `MainActivity`; configuration changes and test doubles are harder than necessary.
3. **Two themes named `PHMSTheme`:** `MainActivity.kt` defines a **dark** Material3 theme used at runtime; `ui/theme/Theme.kt` defines a **light** theme that is **not** used by the app shell (only some color imports in components). Confusing and error-prone.
4. **Dead code:** `UpdateManager.kt` duplicates GitHub update logic but is **never referenced**; active path is `GitHubUpdateChecker` from `MainViewModel`.
5. **Repository leakage:** `MainViewModel` exposes `repository` publicly and reaches into `feedDao` / `marketDao` directly in places instead of going through repository APIs only.
6. **Schema strategy:** `fallbackToDestructiveMigration()` + `exportSchema = false` means **any schema bump can wipe all farm data** on upgrade — unacceptable for production farmers without export/backup.

Reference (`AppDatabase.kt`):


## 5. Security, privacy, and compliance

### Firebase / Firestore

- `google-services.json` is in git (common for mobile, but repo is public).
- `FirestoreBuyerSync` uses collection `shared_buyers` with **read-all / write-from-client** pattern. **Critical:** security depends entirely on **Firestore Rules**. If rules are open, anyone can poison the national buyer directory or scrape contacts.
- **Recommendations:** strict rules (auth or rate limits), moderation flag, validate phone format, optional admin review before `is_community` visibility; never store sensitive farmer PII in shared docs without consent text in-app.

### Android surface

- `android:allowBackup="true"` — farm DB and prefs may be included in **adb backup** unless excluded; consider `android:allowBackup="false"` or backup rules for health/financial data.
- **Release builds:** `isMinifyEnabled = false` — larger APK, easier reverse engineering; no shrink/obfuscation.
- **APK sideload updates** from GitHub — users must trust release signing; document signature/checksum on releases.
- **Permissions:** Camera, notifications, storage/media — justified for photos and exports; ensure runtime permission flows are complete on Android 13+.

### Supply chain

- Dependencies are pinned reasonably (Compose BOM, Room 2.6.1, Firebase BOM). No Dependabot/Renovate or CI vulnerability scan.

**What works:** This is not a loose script collection — it is a **coherent product folder**: app + spec + show report + banner assets + versioned APKs. That is appropriate for **Kitale ASK 2026** and GitHub field distribution.
